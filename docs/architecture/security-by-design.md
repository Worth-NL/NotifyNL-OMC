# Security by design

---

## Information-lean notifications

OMC sends lean notifications (`informatiearm notificeren`) — notifications contain only what is needed to inform the citizen that something has happened, not the full details of the underlying case. This limits the impact of any interception or misdirected delivery.

The safety convention used in example templates reflects this:

> *"Gemeente X stuurt voor uw veiligheid geen e-mails met linkjes."*
> (Municipality X does not send emails containing links, for your security.)

---

## Authentication layers

| Layer | Mechanism |
|---|---|
| Incoming requests to OMC | JWT Bearer token (HS256) |
| OMC → OpenZaak / Besluiten | JWT Bearer token (same HS256 scheme, configured separately) |
| OMC → OpenKlant (v2) | API key |
| OMC → Objecten / ObjectTypen | API key |
| OMC → BRP / Haal Centraal | OAuth2 token exchange (Keycloak) + mutual TLS (mTLS) |
| NotifyNL → OMC callback | JWT Bearer token (long-lived, generated by Secrets Manager) |

---

## JWT security

- JWT secrets should be **at least 64 bytes** long
- Tokens are short-lived (default: 60 minutes) and must be regenerated using the [Secrets Manager](../authentication/secrets-manager.md)
- The callback token used by NotifyNL is long-lived by necessity — treat it as a secret and store it in a secrets manager or Kubernetes secret

---

## mTLS for BRP

All connections to BRP / Haal Centraal use mutual TLS. Both the certificate and private key must be provided as PEM files via environment variables. This ensures that only OMC instances with the correct certificate can query citizen registry data.

---

## No data persistence

OMC is stateless and persists no data. There is no database. All citizen and case data is fetched at request time and discarded after the notification is sent. This limits the blast radius of any potential compromise.
